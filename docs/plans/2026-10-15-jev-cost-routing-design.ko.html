요구사항·현재 근거·세 가지 대안

사용자는 평소처럼 입력합니다. Jev는 작업에 필요한 역량을 판정하고, MindPlayer 코드가 품질 하한을 만족하는 허용 모델 중 비용효율적인 구성을 고릅니다. Jev가 코딩 에이전트나 PIM을 대체하지 않습니다.

  • 새 대화·기존 대화 재개·handoff의 각 새 사용자 턴에서 판정하되 계정·제공자·thread·CWD·권한·승인 절차를 보존합니다.
  • 실행 제공자·계정을 자동 교체하지 않으며 Codex를 Gateway 실행으로 몰래 전환하지 않습니다. 최초 적용 범위는 검증된 Codex입니다.
  • PIM, 자체 학습 모델, 상주 서비스, 대시보드, 신규 SDK 의존성은 범위 밖입니다. 다른 제공자는 어댑터를 증명하기 전 기존 동작을 유지합니다.
접근판정·장점제약·시점
A. 모델 직접 Choice허용 모델 ID와 프로필 중 하나를 Jev가 선택. 가장 작은 PoC.가격 계산과 역량 판단이 섞이고 catalog 변화에 결합됩니다. 비교 기준선.
B. 요구 역량 → 코드 정책Jev는 요구·문맥·위험을 판정하고 코드는 후보 필터·비용 최적화를 담당. 감사와 catalog 변화 대응이 쉽습니다.모델/effort별 검증 프로필과 평가 세트가 필요합니다. 최초 권고.

문맥·개인정보·인증·실패 정책

timeout/401/402/429/TLS/잘못된 답변은 backend 송신 전에만 동일한 login fingerprint·catalog·profile·context 버전이 검증된 last-known 모델로 유지할 수 있습니다. 초기에는 HTTP 자동 재시도나 LLM fallback을 넣지 않습니다. 송신 결과가 불명확하면 재전송하지 않습니다.

0.55.4 구현 상태 · 실제 평가와 구분

HTTP 어댑터·평가 기반 정책·동일 thread 문맥·계정 범위·키 제거·9개 모듈 번들을 연결했습니다. MindPlayer 통합은 길이/키워드 규칙을 사용하지 않으며, 정책이 없으면 네이티브 모델을 그대로 유지합니다. 별도 실행기의 기존 A/B 하네스는 비교용으로 남습니다.

합성 HTTP fixture에서는 같은 thread A→B→A, nonce 보존, 오류/만료/계정 변경의 전송 차단을 검사합니다. 합성 품질·비용 수치는 실사용 근거가 아닙니다. ~/.mindplayer/jev-policy.json의 외부 전송 동의·검증된 전용 키 예산·실제 계정별 평가 프로필을 자동 생성하지 않습니다. 전체 thread token 요구가 미상이면 전환하지 않습니다.

남은 출시 조건은 실제 Gateway TLS/인증·과금, 동의한 holdout 품질/소모 평가, 턴별 전체 문맥·도구 요구의 검증 어댑터, 네이티브 queued/helper 경계의 완전한 E2E입니다. 정적 설정의 token 수는 현재 턴의 측정으로 인정하지 않으며 현재 설치본의 실제 자동 모델 전환은 보류합니다. 현재 검증으로 비용 절감이나 전체 AC 통과를 주장하지 않습니다. 설치본·검증 명령·복구 경로는 tools/local-model-router/jev-integration.validation.json에 기록합니다.

기존 중계와 제안의 차이

로컬 0.55.3은 catalog 기본 모델과 다른 모델 하나를 길이/키워드로 고르는 실험입니다. 순서는 가격·품질 순위가 아니며 Jev와 연결되지 않았습니다. 이 제안은 그 규칙을 의미 판정과 검증 프로필 기반 정책으로 교체합니다. HTML의 A/B는 가상 후보이며 실존 모델의 등급·가격·품질을 뜻하지 않습니다. 네이티브 UI 모델 표시는 지연될 수 있으므로 실제 구현도 요청·서버 수락·관측 증거를 구분해야 합니다.

실행용 입력은 축약·번역하지 않습니다. Jev에는 별도의 제한된 판정용 사본만 보냅니다. 외부 판정이 CWD·계정·명령·도구 승인·권한을 바꾸지 못하게 합니다.

HTTP와 판정 계약

  • 로컬 Node에서 Gateway에 호출하므로 별도 Vercel 배포는 필요하지 않습니다. AI_GATEWAY_API_KEY는 TypeSafe 직접 API 키와 혼용하지 않습니다.
  • 요청의 state·questions, 응답의 answers·usage와 제공되는 비용·generation ID를 검증합니다. Gateway의 정확한 Jev 버전 고정 가능성은 아직 미확인입니다.
  • Vercel의 새 코드 권고인 일반 Decision API와 달리, 이번 안은 TypeSafe 원형 Choice/Noul을 검증하기 위해 호환 HTTP를 택했습니다. 도메인 정책과 전송 어댑터를 분리합니다.
  • 세 질문은 같은 snapshot에 대한 독립 질문입니다. 질문 ID는 모델에 전달되지 않으므로 각 instructions/criteria가 완결돼야 합니다. 다른 질문의 응답을 읽는 방식으로 쓰지 않습니다.
  • Choice confidence는 확률 분포의 집중도이지 정확도나 성공률이 아닙니다. Noul에 별도 confidence를 가정하지 않습니다. 자유 텍스트 추천 모델/이유를 파싱하지 않습니다.
  • AC4는 enum·choice 일치, 유한 숫자, 확률 범위, 빈 분포, 명시한 수치 오차 안의 분포 합계를 모두 검사합니다. LLM fallback의 빈 probabilities/confidence 0은 측정 부재이지 정상 측정값이 아닙니다.

모델 프로필·후보·청구

선택 단위는 제공자 + 실제 계정 + model ID + 지원 reasoning_effort입니다. effort도 품질과 사용량이 달라지는 구성입니다. 필수 프로필은 계정 범위·가용성 확인 시각·모달리티·도구·문맥 한계·작업별 평가 결과와 표본/버전·비용 출처/측정일·지연·청구 방식입니다. 미상은 숫자로 채우지 않습니다.

  • catalog와 명시 허용 목록을 교차하고 알려진 접근 거부 모델은 제외합니다. 필요한 도구·모달리티·문맥·effort 정보를 모르면 하향하지 않습니다.
  • 기존 footer quota 수집을 재사용하되 시각과 계정/pool 범위를 유지합니다. ordinary_usage_allowed=false 또는 명확한 차단은 중단 조건입니다. credits cap만으로 included 사용을 막지 않고 오래된 캐시는 미상으로 처리합니다.
  • 후보 0개는 Jev 없이 오류, 유효 후보가 기존 모델 하나뿐이거나 비교 근거가 없어 바꿀 수 없으면 Jev 생략과 유지 사유를 기록할 수 있습니다. 이를 Jev 판단으로 집계하지 않습니다.
  • 구독 한도·Gateway USD·향후 실행 API USD는 별도로 기록합니다. 모델별 구독 상대 소모가 검증되지 않으면 한도 절약 미검증이며 API 가격으로 환산하지 않습니다.
  • API 실행이 별도 승인된 경우에만 입력·캐시·출력·반복 도구 루프·재작업·모델 변경 캐시 손실·Jev 비용을 같은 통화로 비교합니다. 현재 입력 한 줄만으로 비용을 계산하지 않습니다.

문맥 소유권·키·동시성

  • resume 때 해당 thread의 허용된 사용자/최종 응답만 한 번 읽고 이후 이벤트로 갱신합니다. 정확한 읽기 스키마/호환성은 구현 전에 확인합니다. 전체 파일 재귀 스캔이나 추가 요약 LLM 호출은 기본 경로가 아닙니다.
  • 16 KiB/최대 4쌍은 평가 전 권고값입니다. 질문·criteria를 포함한 전체 요청도 실제 Jev context 한도 아래인지 검사합니다. 잘리거나 참조가 부족하면 그 근거만으로 하향하지 않습니다.
  • 결정 소유권은 pane generation·login fingerprint·thread·request ID·policy/catalog/profile/context 버전에 결합합니다. timeout·종료·계정/문맥 변경 뒤의 응답은 버리고 AbortSignal로 취소합니다. 이미 서버에 도달한 Jev 호출은 과금될 수 있습니다.
  • thread당 pending 판정은 하나입니다. 대기 중 추가 입력은 명시 거부하고 조용히 유실하지 않습니다. 실행 중 steer·approval·tool 응답은 원래 프로토콜로 통과합니다.
  • 현재 active 상태의 turn/start 통과 동작에서 queued 새 턴을 소유할 수 있는지 E2E로 증명해야 합니다. steer를 새 턴으로 바꾸거나 가짜 ACK를 만들지 않습니다.
  • helper/main 출처가 미확인이면 원래 모델 유지와 외부 전송 금지가 안전 조건입니다. main까지 전부 helper로 처리해 비활성인 상태를 합격으로 삼지 않습니다. 다른 thread의 성공만으로 main 라우팅을 입증하지 않습니다.
  • 유지 fallback은 후보 조건과 동일성 검증을 통과할 때만 가능한 새 동작입니다. 그 전에는 현재의 fail-closed를 유지합니다. 현재 모델도 불가하면 입력 보존 후 오류이며 다른 계정·미검증 약한 모델로 전환하지 않습니다.
  • backend 송신 후 결과 불명은 재전송·자동 승격 재실행하지 않습니다. 도구 부작용이 중복될 수 있으므로 작업 자동 재시도는 별도 범위입니다.
  • 현재 run.mjs는 환경을 복사하므로 키를 추가하는 것만으로는 격리되지 않습니다. probe/backend/UI/tools에는 키를 제거하고 합성 canary로 검사합니다. 실제 비밀이나 오류 본문을 출력하지 않습니다.
  • ZDR도 메타데이터 로그 없음은 아니며 법적·계약 예외가 있습니다. 계정 요구·플랜·호환 API 적용 확인 전 보장하지 않습니다. 시스템 curl 성공만으로 Node의 TLS 문제가 해결됐다고 주장하지 않습니다.

예산·품질·출시

  • 전용 키의 서버 측 예산/요청률과 pane별 cooldown·유한 timeout·동시 판정 제한을 둡니다. Gateway 키 예산은 soft cap이고 API 키 호출에는 프로젝트 예산이 적용되지 않으므로 키/팀의 실제 범위를 확인합니다.
  • 여러 Node pane의 합산 USD hard cap은 단일 프로세스 메모리만으로 보장할 수 없습니다. 엄격한 상한에는 공유 원장/예약이 필요하며 v1에는 새 daemon을 추가하지 않습니다.
  • 구현 순서는 정책/평가 계약 → 모의 HTTP 정책 테스트 → 기존 중계/계정 가용성/번들 연결 → 전용 키/TLS의 합성 검증 → 동의한 holdout 평가 → 같은 설치본 E2E입니다. 새 모듈은 Rust 번들 자산에도 포함합니다.
  • 품질 비열등 허용차·표본 수·일반/고위험 집단·한국어/영어/짧은 후속 지시 평가를 live 전에 확정합니다. 성공률·재작업·신뢰구간·판정 p50/p95와 실제 비용을 비교하고 실측 순절감이 없으면 절감 주장을 하지 않습니다.
  • AC1은 모델 A→B→A 및 nonce, AC2는 idle·queued·취소·helper/main 경계, AC5는 stale/Abort/연결 종료/계정·프로필·문맥 변경, AC9는 두 계정 두 pane의 canary 격리를 포함합니다.
