맨 위 판단의 근거 — 직전 조사에서 유지할 것과 수정할 것

옳은 방향: 모델 판단은 선택적 부가기능이고 세션 관리 / CLI 실행은 기본 제품이다. Jev를 강제하면 인증·외부 전송·추가 지연을 원치 않는 사용자까지 같은 의존성을 갖는다. 이는 제품 설계 판단이며 공식 문서가 특정 UI를 요구한다는 뜻은 아니다.

  • Jev는 전달받은 상태에 대해 구조화된 판단을 반환한다. 실행기나 계정 전환기가 아니다. 판단 계층을 선택적으로 두고 실행은 MindPlayer가 관리하는 구분은 적절하다. TypeSafe Choice, 호출 대상을 코드가 실행하는 예제
  • Codex는 같은 thread의 새 turn/start에서 model·effort를 지정할 수 있다. 이전 override가 다음 턴 기본값이 될 수 있으므로 Jev를 껐다고 모델을 임의 초기화하면 안 된다. Codex app-server 계약
  • Subagent와 메인 턴 라우팅은 별개다. Claude의 Advisor / opusplan도 독립적인 네이티브 기능이므로 Jev 미사용에 자동으로 붙이거나 끌 이유가 없다. Codex subagents, Claude Advisor
  • 수정할 가정: “미사용 = 고정 모델”, “effort만 바꾸면 cache 유지”, “자동 선택이면 비용 절감”은 일반화할 수 없다. 모델·버전·연결 방식·작업 성공률에 따라 다르다. Claude cache 조건, OpenAI cache 조건
  • 직전 조사 자료의 effortless 절감률은 제한된 실험 결과이지 이 제품의 비용 증거가 아니다. 여러 도구의 proxy / subagent / effort 조절을 같은 “메인 모델 자동 전환”으로 묶지 않는다. 고정 revision의 실험 범위
  • 판단을 매 새 프롬프트에 요청하는 것과 매번 모델을 바꾸는 것은 다르다. 유지도 가능하다. confidence는 판단의 집중도이지 정답률·권한·비용 절감 증명이 아니다. TypeSafe confidence

결론: 먼저 네이티브 / Jev 두 실행 경로와 명시적 선택을 구현하는 것이 맞다. effort-only·Advisor·역할별 위임·실패 기반 승급은 이번 미사용 경로에 몰래 넣지 말고 별도 기능으로 평가한다. 최저 비용 / 품질 주장은 동일 작업 집합의 성공률·재시도·cache·지연·총사용량 측정 후에만 한다.

UI 대안 3가지 — 왜 공통 열기 전 선택창인가

1. 공통 선택창 · 권장

기존 Enter와 새 세션 생성 모두 같은 단계. 사용 / 미사용과 전송 의미를 바로 알 수 있다. 세션을 여는 순간 한 단계 늘지만 프롬프트마다 묻지 않는다.

2. 열기 명령 / 단축키 분리

“일반 열기 / Jev 열기”는 익숙해지면 빠르다. 하지만 발견성이 낮고 새 세션·기존 세션의 절차가 달라지기 쉽다. 후속 단축 동작 후보.

3. 전역 자동 켜짐 + 예외

조작은 적지만 다른 사용자·키 없는 환경·혼합 모드에서 오해하기 쉽다. 설정 파일이나 키만으로 전송 동의를 추론할 위험. 주 경로로 채택하지 않는다.

표현 방식도 비교했다: 정적 이미지 / SVG는 상태 조작이 어렵고, 별도 프런트엔드 앱은 의존성이 늘어난다. 이 시안은 외부 라이브러리 없는 HTML·CSS·소량의 JS로 화면과 전환을 함께 검증한다.

선택의 수명 — 기존 세션·새 세션·이름 변경·실행 중 복귀
  • 새 / 기록 없는 기존 세션: 미사용 기본값 제안. Jev 설정이 있어도 자동 선택하지 않는다. 선택창은 PTY 생성 전이며 취소하면 생성·실행·기록을 하지 않는다.
  • 다음 재개: 마지막 유효 선택을 미리 보여주는 안을 권장한다. provider + accountFingerprint + 실제 threadId로 기록하고 계정 이름·세션 제목으로 묶지 않는다. 새 세션은 실제 ID가 확인된 뒤 기록한다.
  • 같은 세션: 선택 변경만으로 새 thread를 만들지 않는다. 계정·대화·권한은 유지한다. Jev 미사용 시 마지막으로 유지된 모델·effort도 억지로 초기화하지 않는다.
  • 이미 실행 중: 재연결과 재개를 구분한다. 적용 모드는 읽기 전용이다. 진행 중인 작업·대기 큐를 중단 / 폐기 / 재전송하지 않으며 안전하게 종료한 뒤 다시 열 때 변경한다.
  • 동의: 키와 선택 기록은 외부 전송 동의가 아니다. 별도 유효 동의 버전 / 서비스 / 범위를 확인한다. 이미 유효하면 체크를 재사용할 수 있다. 시연은 동의 없는 경우를 보여준다.
  • Handoff: 대상 새 실행에서도 선택한다. 원본 계정의 모드나 외부 전송 동의를 자동 상속하지 않는다. 일괄 열기의 개별 확인 UX와 실행 중 즉시 전환은 후속 범위다.
키 없음·전송 금지·미지원·판단 실패는 어떻게 보이는가
  • Jev 미사용에는 Jev 인증을 요구하지 않는다. 네이티브 CLI 로그인·사용 제한·실행 환경은 별도로 충족해야 한다.
  • 사용을 골랐는데 키 없음 / 정책 금지 / 미지원이면 원인과 “미사용으로 변경”을 보여준다. 자동으로 바꾸거나 키를 화면에 출력하지 않는다. 키가 있어도 인증·잔액·네트워크 성공은 미확인이다.
  • Jev 선택은 CLI의 계정 사용 제한이나 외부 전송 금지 정책을 무효화하지 않는다. 계정·모델·effort의 실제 후보 자격도 별도 검사한다.
  • 실행 전 판단이 실패하면 “판단 실패 · 실행 미전송”. 네이티브 실행에 보낸 뒤 결과 불명은 별도 상태다. 두 상태 모두 입력을 자동 재전송하지 않는다.
  • Jev 판단 서비스 / 경유 서비스의 이름과 전송 범위를 동의에 표시한다. 현 계약은 현재 입력 + 제한된 직전 판단 + 후보 / 기준이다. 전체 대화 paging·요약 에이전트는 추가하지 않는다.
  • 미사용 모드의 CLI 내부 Advisor 등 네이티브 기능은 자체 오류 / fallback 계약을 따른다. MindPlayer의 Jev 오류 정책과 혼동하지 않는다.
