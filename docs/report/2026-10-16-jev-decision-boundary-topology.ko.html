MINDPLAYER → JEV / 제안 계약

무엇을 전달하나

모델 이름만 주고 알아서 맞히라고 하지 않는다. 후보의 제공된 설명과 판단 기준을 함께 준다.

{
  model: "설정된 Jev 모델",
  state: {
    currentInput: "사용자가 입력한 원문",
    baseline: { model, effort },
    previousDecision: "같은 세션의 제한된 상태 또는 unknown",
    contextKnown, truncated, attachments
  },
  questions: {
    configuration: {
      type: "choice",
      instructions: "버전이 고정된 우리 판단 기준",
      criteria: {
        c0: "현재 모델+effort 및 제공된 설명",
        c1: "다른 적격 모델+effort 및 제공된 설명"
      }
    }
  }
}

구조 설명용 의사 코드. previousDecision은 제안이며 아직 구현되지 않음. 현재 코드는 제한된 최근 user/final-assistant 대화를 보냄. 전체 직렬화 크기는 제한하고, 누락·절단은 명시한다.

JEV → MINDPLAYER / 공식 CHOICE 계약

무엇을 돌려받나

Jev는 전달한 선택지 중 하나를 반환한다. 자유 형식의 모델 설정이나 설명문을 생성하는 계약이 아니다.

answers.configuration = {
  type: "choice",
  choice: "공급한 후보 ID 중 하나",
  probabilities: { /* 모든 후보 ID의 확률 */ },
  confidence: /* 분포에서 계산한 값 */
}

// 아래는 MindPlayer 내부에서만 수행
const target = boundCandidates[answer.choice];
validate(answer, target, currentVersions);
submitOriginalTurn({
  ...originalParams,
  model: target.model,
  effort: target.effort
});

실측 응답이 아닌 계약 예시. confidence는 정답률이 아니다. 후보 수에도 영향을 받으므로 임의의 “0.8이면 안전” 같은 기준을 넣지 않는다. 추가 진단 질문들은 같은 state를 보지만 서로의 답을 읽지 못한다. Confidence · State

LIFECYCLE / 새 사용자 턴마다 반복

세션 진입부터 다음 프롬프트까지

① 세션 진입

기존 네이티브 화면. 적격 후보와 정확한 현재 설정을 확보. 진입만으로 코딩 모델을 임의 변경하지 않음.

② 프롬프트 제출

전제조건을 만족한 새 턴마다 Jev 호출. 같은 모델을 선택해도 정상적인 판단 결과.

③ 실행 중

선택한 설정으로 한 턴 진행. 도구 결과·steering·중간 출력마다 재판단하지 않음.

④ 다음 사용자 입력

현재 후보와 새 입력으로 다시 판단. 이전 결정은 작은 로컬 상태로만 이어 받도록 제안.

현재 통합 경로는 Codex 대상. Claude·Kiro·Cursor가 같은 자동 선택을 이미 지원한다는 의미는 아님.

판단 기준 — 모델 등급표가 아니라, Jev가 비교할 규칙

아래는 제안하는 제품 기준이야. MindPlayer가 기준을 정의하고 버전 관리하지만, 각 프롬프트가 어느 기준에 해당하는지와 어떤 후보가 적절한지는 Jev가 판단한다.

Jev가 의미로 판단

  • 해결 공간: 해야 할 변경이 구체적인가, 원인·방법부터 찾아야 하는가?
  • 조정 부담: 독립적인 단순 작업인가, 여러 단계·컴포넌트를 연결해야 하는가?
  • 실패 영향: 배포·장애·권한·데이터 손실처럼 틀렸을 때 영향이 큰가?
  • 이어지는 작업: 짧은 후속 지시가 진행 중인 복잡한 작업을 이어가는가? 짧다고 낮추지 않는다.
  • 정보 부족: 현재 입력과 제한된 상태만으로 비교할 수 있는가? 모르면 추측하지 않고 현재 적격 설정 유지.

MindPlayer가 코드로 보장

  • 같은 제공자·계정의 허용된 모델 및 지원 effort만 후보에 포함.
  • 알려진 입력·도구·컨텍스트 요구사항과 충돌하는 후보 제외. 모르는 요구사항을 알고 있다고 취급하지 않음.
  • 후보 순서·모델 이름으로 성능이나 비용을 추정하지 않음.
  • 비용·품질 실측이 없다면 “충분한 후보 선택”으로 표현. 최저 비용·품질 보장은 주장하지 않음.
  • 실측 기반 정책이 설정돼 있다면 그 정책의 검증 조건을 그대로 적용. 설명 기반 선택으로 몰래 우회하지 않음.
한 번의 API 호출에 작업 분류와 후보 선택을 같이 물을 수는 있다. 하지만 두 질문은 독립적이다. “첫 답을 보고 둘째 답을 고른다”가 아니라, 후보 선택 질문 자체에 필요한 기준을 모두 넣는다. 공식 State 계약
네가 제시한 6개 예시 — Jev가 볼 신호만 정하고, 모델은 미리 찍지 않기

아래는 실제 Jev 결과가 아니다. 단어 하나로 모델을 고정하지 않고, 이 차이를 판단하도록 기준에 넣자는 예시야.

1. 설계안을 만들어줘

기존 템플릿 정리인지, 해결되지 않은 요구사항·트레이드오프를 새로 설계하는지 구분. “설계”라는 단어만으로 최상위 모델 고정 금지.

2. 이 line이 잘못됐으니까 수정해

정답과 범위가 명확한 작은 수정인지, 그 한 줄이 동시성·보안·데이터 무결성과 연결되는지 판단.

3. 개발 다 하고 PR 만들어

남은 개발·검증·여러 변경 조정이 있는지, 이미 완료된 작업의 PR 생성만 남았는지 판단. 이전 판단 상태가 없으면 완료를 단정하지 않음.

4. 머지 확인 후 릴리즈·배포

절차가 알려져 있어도 외부 영향·실패 복구 부담이 큼. 모델 선택과 배포 권한은 별개이고, 선택이 새 실행 권한을 주지 않음.

5. daily report 작성해

모인 자료의 정리인지, 여러 소스 수집·충돌 확인·원인 해석까지 필요한지 판단. 문서 작업이라는 이유만으로 단순화 금지.

6. 장애 분석해

미지의 원인·가설 비교·영향 범위·불확실성을 고려. 이미 확정된 분석의 요약인지도 구별하되, 정보가 없는데 원인을 안다고 가정하지 않음.

긴 세션·“계속해”·compact·동시 세션은 어떻게 다루나

전체 대화를 매번 보낼 필요는 없음

이번 목적은 대화 내용의 정답을 생성하는 것이 아니라, 필요한 작업 부담과 적절한 후보를 판단하는 것. 현재 프롬프트 우선 + 작은 이전 판단 상태를 제안한다.

이전 상태에는 마지막 유효 설정, 미해결/진행 중 여부처럼 범위가 제한된 정보만 둔다. 이를 모르면 unknown. 새 요약 에이전트나 전체 히스토리 paging을 기본 경로에 추가하지 않는다.

“계속해”도 Jev를 호출하되, 현재 정보만으로 하향 선택을 정당화할 수 없으면 기존 적격 설정 유지. 현재 코드는 최근 최대 4쌍을 사용하므로 이 부분은 제안 변경이다.

세션 구분은 MindPlayer가 담당

로컬에서 계정·세션·요청·세대·카탈로그·기준 버전에 판단을 바인딩한다. 다른 세션의 상태를 섞지 않고, 늦게 도착한 응답을 다음 요청에 재사용하지 않는다.

compact 뒤에도 기준과 로컬 판단 상태는 대화 원문과 독립적으로 관리하도록 제안한다. 단, 상태가 오래됐거나 불명확하면 모른다고 표시하고 보수적으로 유지.

이 설계는 완전한 맥락 이해를 보장하지 않는다. 숨겨진 복잡성을 놓치는지는 별도 평가해야 한다. 현재 Codex 실행 경로의 실제 컨텍스트 한도를 프롬프트 길이로 추정하지 않는다.

유지와 실패를 구분 — 안전장치와 테스트할 조건

정상 유지 ≠ 판단 실패

  • 유효한 Jev 결과가 현재 후보 선택: 판단 성공, 모델 유지, 턴 실행.
  • 판단 결과는 유효하지만 안전 조건 불충족: 기존 정책대로 적격 baseline 유지 또는 명시적 거절. 임의 대체 모델 없음.
  • 네트워크·인증·응답 형식 오류: 전송 전 실패를 원인과 함께 표시. 판단했다고 꾸미거나 자동 재시도·몰래 전송하지 않음.
  • 이미 전송한 뒤 응답이 불확실: 같은 프롬프트를 자동 재전송하지 않음.

후속 구현의 합격 기준

  1. 적격 새 입력마다 실제 Jev 호출 정확히 한 번. 유지 결과도 포함.
  2. 다른 세션·계정·옛 기준 응답 적용 0건.
  3. 원문·thread·권한 보존, model+effort만 일관되게 적용.
  4. 짧은 후속 지시·긴 세션·compact·중단·연속 입력 회귀 테스트.

공식 문서 · 구성도 표현 방식 선택

Jev 계약 근거

  • TypeSafe Choice — caller가 후보와 설명을 제공. ID 선택 결과를 코드가 해석.
  • TypeSafe API — answers / choice / probabilities / confidence.
  • State — 입력 데이터와 독립 질문. 영속 세션 저장 API로 해석하지 않음.
  • Confidence — 분포 기반 값과 실제 정확도 구분.
  • Function calling cookbook — 선택 결과를 실제 동작으로 연결하는 책임은 코드에 있음.
